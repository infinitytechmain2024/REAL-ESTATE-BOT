# Поиск по сайтам (веб-этап кампаний)

Каждая кампания, кроме групп Facebook, параллельно ищет объявления на сайтах.
Этап работает внутри сервиса `campaign-runner` отдельным циклом
(`bot/web_search`), поэтому не задерживает Facebook и не зависит от него. Место
этапа в общей схеме: [ARCHITECTURE.md](ARCHITECTURE.md).

## Как это работает

1. **План поиска** (`SearchPlan`, раздел ниже): один вызов модели на кампанию
   даёт порталы с приоритетом, запросы по языкам и прямые адреса поиска
   порталов с уже выставленными фильтрами.
2. **Запросы.** Первый раунд берёт запросы плана. Дальше модель
   (`OPENROUTER_WEB_QUERY_MODEL`, тот же `OPENROUTER_API_KEY`) пишет раунд из
   `WEB_SEARCH_QUERIES_PER_ROUND` новых запросов на es/en/ru/uk: другие
   формулировки, синонимы, пригороды, запросы `site:` по порталам. Ей передаются
   все уже использованные запросы. Похожие по смыслу отбрасываются (регистр,
   ударения, порядок слов, окончания, служебные слова; совпадение слов ≥ 75 %).
   Каждый запрос называет тип объекта, бюджет, комнаты, место и страну. Всего не
   больше `WEB_SEARCH_MAX_QUERIES_PER_CAMPAIGN`. Без ключа или при сбое модели
   запросы строятся по шаблонам.
3. **Поиск.** Запрос уходит в бэкенды (раздел «Поисковые бэкенды»): по умолчанию
   во внутренний SearXNG (сервис `searxng`, настройки
   `docker/searxng/settings.yml`: только JSON, limiter выключен, порт наружу не
   открыт). Для запроса берутся `WEB_SEARCH_PAGES_PER_QUERY` страниц выдачи и не
   больше `WEB_SEARCH_RESULTS_PER_QUERY` результатов.
4. **Очередь страниц.** Из выдачи в очередь кампании встают новые адреса.
   Страница поиска портала (список объявлений) сама не сохраняется: из неё берутся
   ссылки на объявления того же сайта (не больше `WEB_SEARCH_MAX_LINKS_PER_INDEX`),
   и читаются они. Ссылки из JSON-LD `ItemList` идут в очередь первыми.
5. **Чтение страницы** слоями HTTP, браузер, scrape API (раздел «Слои чтения»).
6. **Данные сайта в JSON** (`bot/web_search/structured.py`, Scrapling). Порталы
   кладут объявления в разметку schema.org JSON-LD (`RealEstateListing`, `Offer`,
   `Apartment`, `House`, `ItemList` …) и OpenGraph. Парсер Scrapling (`Selector`,
   без запросов и браузера) достаёт их в плоский JSON: `title`, `url`, `price`,
   `currency`, `area_m2`, `rooms`, `address`, `property_type`, `deal`,
   `description`. Строка «JSON-LD: {…}» ставится в начало текста объявления, и
   анализ сверяет точные цифры сайта с задачей.
7. **Объявление → находка.** Текст записывается в `collected_posts` так же, как
   пост Facebook: сайт — это `monitoring_sources` (platform `website`), чтение —
   `acquisition_runs` внутри веб-пакета кампании. Дальше всё штатно: анализ
   (Sonnet, `analysis-v6`), правила ±10 %, рецензент, дедуп «Также на», карточка
   со ссылкой на конкретное объявление.

Если на странице сайта ничего не прочитать (отказали все слои, запрет
`robots.txt`), остаётся карточка из заголовка и фрагмента результата поиска
(миграция `029_web_search_snippets.sql`).

Статус для пользователей: «Ищу в интернете…», «Ищу на сайте fotocasa.es…» и
живая строка «Сейчас: сайты · idealista.com (браузер) · прочитано 37 · найдено 12
· порталов 4/8», в конце «Сайты: готово · прочитано N · найдено M» (слой:
напрямую, браузер или API). Владельцы видят техническую строку и «Сайты:
<хост>: отказы напрямую 3, браузер 1 · карточек отправлено N». Кампания не
завершается, пока веб-этап ещё ищет.

## План поиска (SearchPlan)

Перед первым раундом запросов модель (`OPENROUTER_PLAN_MODEL`, по умолчанию
`anthropic/claude-sonnet-4.5`, рекомендуется `anthropic/claude-opus-5.5`; таймаут
`OPENROUTER_PLAN_TIMEOUT_SECONDS`, 45 с, температура 0.3, один вызов на
кампанию) по ТЗ (`TaskSpec`) пишет `SearchPlan` (`bot/campaign/search_plan.py`):

- `sites`: порталы с приоритетом 1–3;
- `queries`: 5–15 запросов на язык (es и en, плюс ru и uk, если человек писал на
  них); в каждом тип объекта, сделка, место со страной, бюджет и комнаты;
- `portal_urls`: прямые страницы поиска портала с фильтрами (idealista,
  fotocasa, pisos.com, habitaclia), только шаблоны, в которых модель уверена;
- `stop` (правило остановки) и `notes`.

Модель предлагает, код решает: хост должен быть в списке порталов страны
(`urls.SPAIN_PORTALS_BY_KIND`, `UKRAINE_PORTALS`) или в `spec.sources`, иначе
отбрасывается; запросы без повторов по смыслу, не больше 15 на язык и 60 всего;
хосты из `spec.sources.blocked` вычищаются.

План сохраняется в `campaigns.plan.search_plan` один раз и дальше используется:

- первый раунд берёт запросы плана, остаток раунда дописывают модель запросов и
  шаблоны;
- `portal_urls` ставятся в очередь как страницы поиска (глубина 0) до первого
  поиска;
- порядок обязательных порталов: сначала `sites` плана по приоритету, потом
  список по виду объекта (для Испании Idealista и Fotocasa первыми; для земли
  затем Terrenos.es и Sareb); `WEB_SEARCH_COVER_PORTALS=false` отключает
  обязательный обход;
- сайты из `spec.sources.blocked` не ищутся, не читаются и не попадают в очередь.

Без ключа, при сбое или пустом ответе плана нет, и этап работает по шаблонам.
`CAMPAIGN_SEARCH_PLAN_ENABLED=false` отключает планировщик.

## Поисковые бэкенды

По умолчанию ищет только SearXNG. `WEB_SEARCH_BACKENDS` — список через запятую
из `searxng`, `google_cse`, `serpapi`; несколько бэкендов опрашиваются
параллельно, выдача сливается по кругу (по одному результату от каждого) без
дублей по адресу страницы. Сбой одного бэкенда логируется
(`web_search.backend_failed`) и не мешает остальным. Google CSE
(`GOOGLE_CSE_API_KEY`, `GOOGLE_CSE_CX`; 100 бесплатных запросов в сутки) и SerpAPI
(`SERPAPI_API_KEY`; платный) ограничены `WEB_SEARCH_GOOGLE_CSE_DAILY_CAP` и
`WEB_SEARCH_SERPAPI_DAILY_CAP` (по 90 в сутки). Счётчик хранится в памяти
процесса по дням UTC и сбрасывается при перезапуске. Бэкенд без ключа
пропускается.

## Слои чтения страницы

Читаются только публичные GET-страницы: без логинов, форм и cookies, только
публичные адреса (проверка на каждом из не более 4 редиректов), только HTML,
лимит размера и таймауты. `robots.txt` читается один раз на сайт и соблюдается
вместе с `Crawl-delay` (не больше 30 с); не чаще одного запроса к сайту в
`WEB_SEARCH_HOST_INTERVAL_SECONDS` (5 с). Страница, запрещённая `robots.txt`, не
читается ни одним слоем.

**Слой 1: HTTP.** Обычный GET. По умолчанию (`WEB_SEARCH_IMPERSONATE=chrome`;
`off`, `chrome`, `safari`, `firefox` или точный профиль curl_cffi, например
`chrome124`) страницы читаются через `curl_cffi` с TLS/HTTP2-отпечатком браузера,
UA Chrome 124 для Windows (`WEB_SEARCH_BROWSER_USER_AGENT`), `Accept-Language` по
стране (ES, UA), `Sec-Fetch-*`. `off` или отсутствие `curl_cffi` — обычный httpx с
объявленным UA бота. Неизвестное значение при загрузке даёт предупреждение и
заменяется на `chrome`. `robots.txt` всегда сверяется с объявленным UA бота,
хотя страницы читаются с браузерным отпечатком.

**Слой 2: браузер** (`bot/web_search/render.py`, путь Agent Reach). Страница
читается ещё раз в сервисе `browser`: отдельный профиль без входа в аккаунты,
одна страница на аренду, таймаут `WEB_SEARCH_RENDER_TIMEOUT_SECONDS`, не больше
`WEB_SEARCH_MAX_RENDERS_PER_CAMPAIGN` страниц на кампанию (счёт в базе, не
сбрасывается перезапуском). Берутся текст, ссылки и JSON-LD. В браузер страница
идёт в двух случаях: сайт ответил HTTP 200, но текста нет (рисуется JavaScript),
или сайт отказал (403/429/503) либо отдал капчу (короткий текст «captcha»,
«datadome», «are you a robot», «access denied»). Второе отключается
`WEB_SEARCH_RENDER_ON_REFUSAL=false`; отказанная страница поиска портала
(глубина 0) может идти в браузер, пока `WEB_SEARCH_RENDER_INDEX_ON_REFUSAL=true`.
Весь слой отключается `WEB_SEARCH_RENDER_ENABLED=false`.

**Слой 3: scrape API** (`bot/web_search/scrape_api.py`, по умолчанию выключен).
Если заданы `WEB_SEARCH_SCRAPE_API_URL` и `WEB_SEARCH_SCRAPE_API_KEY` и отказали и
HTTP, и браузер, делается `GET <URL>?url=<адрес страницы>` с заголовком
`Authorization: Bearer <ключ>` (общий вид для Zyte, ScraperAPI, Bright Data).
Ответ проверяется как обычная страница (только HTML, лимит размера, таймаут, без
редиректов). Не больше `WEB_SEARCH_MAX_SCRAPE_API_PER_CAMPAIGN` страниц на
кампанию (счёт в базе). Страницы поиска портала сюда не попадают никогда: только
объявления и ссылки глубины 1. Ключ нигде не логируется; адрес API может вести на
любой доверенный владельцу хост.

**Блокировка по слоям** (миграция `034_web_fetch_layers.sql`). Три отказа подряд
на слое блокируют на 12 часов только этот слой этого сайта
(`web_hosts.http_blocked_until`, `render_blocked_until`); успех обнуляет счётчик.
Пока HTTP заблокирован, страницы сайта сразу идут в браузер, без запроса HTTP.
Когда заблокированы все включённые слои, сайт не опрашивается вообще, остаются
карточки из результатов поиска (`blocked_until`, «все слои заблокированы»).
Scrape API блокировки не имеет: пока он включён, сайт целиком не блокируется. Без
браузера (`WEB_SEARCH_RENDER_ENABLED=false`) единственный слой — HTTP.
Слой, которым прочитана страница, пишется в `web_campaign_urls.layer` (миграция 039)
и учитывается в итогах кампании (`campaign_metrics`).

## Что читается один раз, а что заново

Миграция `021_campaign_web_search.sql`, таблицы:

- `web_seen_urls`: каждая страница, которую бот когда-либо брал в работу, по
  `url_key` (SHA-256 нормализованного адреса: без `www.`, `#…`, `utm_*`). **Объявление
  читается один раз для всей системы:** тот же адрес из другого запроса или другой
  кампании пропускается (`duplicate`), и вторая кампания его не получит. Исключение
  — страница поиска портала (`index`): она читается заново через
  `WEB_SEARCH_INDEX_TTL_DAYS` (7 дней; 0 — не перечитывается; миграция 032), а ссылки
  на ней проходят ту же проверку: новые объявления портала берутся, прочитанные нет.
  Пока TTL не истёк, страница поиска не перечитывается, и повторный запуск той же
  задачи в этот срок может не принести новых объявлений с неё.
- `web_campaign_urls`: очередь и журнал кампании (`queued`, `fetched`, `failed`,
  `duplicate`, `capped`, `robots`, `skipped`).
- `web_hosts`: каждый сайт, его источник, счётчики и блокировки по слоям.
- `web_search_queries`: запросы кампании. Свой запрос кампания не повторяет никогда;
  при `WEB_SEARCH_QUERY_REUSE_HOURS` > 0 запрос, искавшийся другой кампанией за это
  время, пропускается (по умолчанию 0: можно повторять).

## Лимиты

Все значения по умолчанию совпадают с `.env.example` и настройками
(`bot/web_search/settings.py`).

| Переменная | По умолчанию | Что ограничивает |
|---|---|---|
| `WEB_SEARCH_MAX_QUERIES_PER_CAMPAIGN` | 80 | запросов на кампанию |
| `WEB_SEARCH_QUERIES_PER_ROUND` | 12 | запросов в раунде |
| `WEB_SEARCH_RESULTS_PER_QUERY` | 30 | результатов с одного запроса (после слияния страниц) |
| `WEB_SEARCH_PAGES_PER_QUERY` | 2 | страниц выдачи SearXNG на запрос (1–5; остановка, если страница не дала новых ссылок) |
| `WEB_SEARCH_QUERY_REUSE_HOURS` | 0 | часов, в течение которых запрос другой кампании пропускается (0: не пропускается) |
| `WEB_SEARCH_MAX_PAGES_PER_CAMPAIGN` | 400 | страниц на кампанию |
| `WEB_SEARCH_MAX_PAGES_PER_HOST` | 100 | страниц одного сайта на кампанию |
| `WEB_SEARCH_MAX_PAGES_PER_UNKNOWN_HOST` | 5 | страниц сайта, не являющегося известным порталом, пока он не дал ни одного объявления |
| `WEB_SEARCH_MAX_LINKS_PER_INDEX` | 40 | ссылок со страницы поиска портала |
| `WEB_SEARCH_INDEX_TTL_DAYS` | 7 | через сколько дней страница поиска портала читается заново (0: не читается) |
| `WEB_SEARCH_MAX_RENDERS_PER_CAMPAIGN` | 60 | чтений в браузере на кампанию (считается в БД) |
| `WEB_SEARCH_MAX_SCRAPE_API_PER_CAMPAIGN` | 40 | чтений через scrape API на кампанию (если задан `WEB_SEARCH_SCRAPE_API_URL`) |
| `WEB_SEARCH_MAX_PAGES_PER_DAY` | 3000 | страниц за 24 ч на всю систему |
| `WEB_SEARCH_MAX_QUERIES_PER_DAY` | 300 | запросов за 24 ч на всю систему |
| `WEB_SEARCH_MAX_MINUTES_PER_CAMPAIGN` | 240 | длительность веб-этапа кампании |
| `WEB_SEARCH_HOST_INTERVAL_SECONDS` | 5 | пауза между двумя запросами к одному сайту |
| `WEB_SEARCH_GOOGLE_CSE_DAILY_CAP` / `WEB_SEARCH_SERPAPI_DAILY_CAP` | 90 / 90 | запросов к платному бэкенду в сутки |

Веб-этап кампании заканчивается, когда достигнут любой из лимитов на кампанию или
на систему либо кончилась очередь и раунды запросов.
`WEB_SEARCH_ENABLED=false` выключает этап. Сайт можно запретить навсегда
(`WEB_SEARCH_BLOCKED_HOSTS`; соцсети пропускаются всегда) или поставить на паузу
его источник (`/pause source:<id>`, id — в `monitoring_sources`,
`canonical_url = https://<сайт>/`).

## Прокси / VPN

`WEB_SEARCH_PROXY_URL` (`http://host:port` или `socks5://host:port`) — через него
идут и чтение страниц, и исходящие запросы SearXNG. Пусто — напрямую. Можно
перечислить несколько прокси через запятую: каждый сайт закреплён за одним
(`crc32(host) % n`), чтобы видеть один IP; следующий берётся только если к
выбранному не удалось подключиться. Значение прокси не пишется в логи. Для
порталов с защитой нужны резидентские или ISP-адреса: адрес дата-центра VPS
главный сигнал для таких защит.

Подключить WireGuard через [gluetun](https://github.com/qdm12/gluetun):

1. В `docker-compose.yml` раскомментируйте сервис `gluetun` (пример рядом с
   `searxng`).
2. В `.env` задайте `GLUETUN_VPN_PROVIDER` (или `custom`),
   `GLUETUN_WIREGUARD_PRIVATE_KEY`, `GLUETUN_WIREGUARD_ADDRESSES`,
   `GLUETUN_WIREGUARD_PUBLIC_KEY`, `GLUETUN_WIREGUARD_ENDPOINT_IP`,
   `GLUETUN_WIREGUARD_ENDPOINT_PORT` из конфигурации вашего VPN.
3. `WEB_SEARCH_PROXY_URL=http://gluetun:8888` (HTTP-прокси gluetun).
4. `docker compose up -d gluetun searxng campaign-runner`.

```sh
git pull

docker compose pull searxng
docker compose up -d --build searxng campaign-runner
```

Какие переменные `.env` доходят до `campaign-runner`, определяет блок
`environment` этого сервиса в `docker-compose.yml`.

## Риски

- Крупные порталы (idealista, fotocasa) защищены от ботов (DataDome и т. п.) и
  часто отвечают 403 на обычный HTTP-клиент. Отказанная страница пробуется в
  браузере и, если настроен, через scrape API; после трёх отказов слой блокируется
  на 12 часов, а когда отказали все слои, остаются карточки из результатов поиска.
  `robots.txt` не обходится никогда. Объявления с агентских сайтов и классифайдов
  читаются лучше. Резидентский прокси помогает, но не гарантирует.
- Поисковики внутри SearXNG иногда отдают CAPTCHA или лимит: запрос возвращает
  мало результатов (в логе `web_search.engines_silent`). Второй бэкенд
  (`google_cse`) снижает эту зависимость.
- Объявление, прочитанное одной кампанией, другой кампании не показывается заново
  (см. «Что читается один раз»): повторный запуск той же задачи получает только
  объявления, которых ещё не видела система, поэтому новые находки появляются
  после перечитывания страниц поиска (через `WEB_SEARCH_INDEX_TTL_DAYS`) и с новых
  запросов.

## Фильтры бюджета страниц (против словарей, новостей и чужой сделки)

- **Запрос**: для вертикали `real_estate` запрос без слова об объекте (piso, casa, terreno, квартира, flat …) отбрасывается в `localise` (лог `web_search.query_dropped`).
- **Выдача (SERP)**: хит отбрасывается, если сайт не известный портал (`PORTALS`, списки стран, сайты плана и `spec.sources`) и в заголовке+сниппете нет слова об объекте И числа с ценой (€), площадью (m²) или комнатами (hab.). Просто слово «precio» не считается. Счётчик в логе `web_search.serp_dropped`.
- **Чёрный список** (`urls.NON_LISTING_HOSTS`, `NON_LISTING_BRANDS`, `NON_LISTING_PATHS`): словари, калькуляторы, `*.gob.es`/`*.gov`, новости и ТВ, транспорт, путеводители, `idealista.com/news/`.
- **Неизвестный сайт**: не больше `WEB_SEARCH_MAX_PAGES_PER_UNKNOWN_HOST` страниц на кампанию, пока он не дал ни одного объявления.
- **Сделка**: при `deal=sale` ссылки с `/alquiler`, `/rent`, `/оренда` … (и хиты порталов с таким путём) пропускаются; при `deal=rent` — `/venta`, `/comprar`, `/for-sale`, `/продаж`.
