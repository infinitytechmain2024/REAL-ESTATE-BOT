# Ревʼю проєкту та план доробки (жовтень 2026)

Документ для власника: чому бот видає слабкі результати, які ліміти стоять
зараз, і що треба зробити, щоб бот (1) допитував задачу, (2) шукав без
штучних обмежень по всіх обовʼязкових сайтах і (3) віддавав лише те, що
проходить критерії. Два режими: «Обʼєкти нерухомості» та «Інвестори».

## 1. Як влаштовано зараз (коротко)

```
Telegram → intake (gpt-4o-mini, ≤3 питання) → plan_campaign (regex, без LLM)
   ├─ Facebook: пошук груп → вікна по 20 груп → 15 постів/група
   ├─ Сайти: gpt-4o-mini пише запити → SearXNG (1 сторінка, 10 результатів) → httpx GET → JSON-LD
   ├─ Соцмережі (TikTok/Instagram/LinkedIn) через браузерні профілі
   └─ Інвестори: reach.py (тільки сніпети пошуковика) + коментарі під постами FB
posts → analysis-worker (gpt-4o-mini, «це нерухомість?») → tolerance (правила ±10 %)
      → relevance (gpt-4o-mini, 200 викликів/кампанію) → картка exact / similar / other / excluded
```

Сильна модель (`claude-opus-5.5`) підключена лише у `reduction-worker`, який
працює в «тіньовому» режимі, вимкнений за замовчуванням і нічого не надсилає.

## 3. Поточні ліміти (що саме обмежує «не все, що знайшов»)

| Змінна | Зараз | Ефект |
|---|---|---|
| `WEB_SEARCH_MAX_QUERIES_PER_CAMPAIGN` | 40 | ~20 з них зʼїдають примусові `site:` по 20 порталах |
| `WEB_SEARCH_RESULTS_PER_QUERY` / `pageno` | 10 / тільки 1 сторінка | не бачимо результатів 11+ |
| `WEB_SEARCH_MAX_PAGES_PER_CAMPAIGN` | 150 | |
| `WEB_SEARCH_MAX_PAGES_PER_HOST` | 30 | один портал ≤ 30 оголошень на кампанію |
| `WEB_SEARCH_MAX_LINKS_PER_INDEX` | 10 | з індексної сторінки беремо лише 10 посилань |
| `WEB_SEARCH_MAX_PAGES_PER_DAY` | 1500 | на всю систему |
| `WEB_SEARCH_MAX_RENDERS_PER_CAMPAIGN` | 15 | скидається при рестарті |

| `web_seen_urls` | назавжди | повторний пошук майже порожній |

Підняти цифри в `.env` можна за хвилину, але це не вирішить головного:
ключові портали не читаються (403), запити будуються неправильно, а фільтр
пропускає зайве. Тому план нижче — архітектурний, а не «підкрутити ліміти».

## 4. Цільова архітектура: ланцюг агентів

Принцип: **дорога модель думає, дешева — парсить, середня — перевіряє.**

```
1. Інтервʼюер (Fable/Opus)  — «grill me»: допитує до повного ТЗ, формує TaskSpec (hard/soft критерії)
2. Архітектор (Fable/Opus)  — план пошуку: сайти, запити по мовах, сторінки, стоп-критерії
3. Збирачі (Sonnet + код)   — пошук + скрапінг + витяг полів у строгий JSON (ціна, м², кімнати, адреса, контакт)
4. Рецензент (Opus)         — перевіряє кожну знахідку проти TaskSpec: hard-критерії → pass/fail з доказом (цитата)
5. Фіналіст (Fable)         — дедуп, кластери «той самий обʼєкт», ранжування, фінальний звіт + причини відмов
```

`TaskSpec` (нова таблиця `campaign_specs`, JSONB):
- `hard`: місто (+ ISO країна, рівень: місто/провінція/регіон, список районів або радіус), угода, тип, бюджет min/max + валюта, кімнати min/max, площа min/max, обовʼязкові атрибути (тераса, ліфт, паркінг …), для інвесторів: тікет min/max, клас активу, дохідність, географія, роль (шукаємо гроші / шукаємо куди вкласти).
- `soft`: побажання з вагами.
- `exclude`: що точно не треба.
- `sources`: обовʼязкові сайти (із списку клієнта), додаткові, заборонені.
- `delivery`: скільки знахідок, стрім чи пачкою, чи показувати «схожі».

## 5. План доробки по етапах

### Етап 0. Швидкі фікси (1–2 дні) — дають ефект одразу
1. Міграція `031`: розширити CHECK кроку (`ask`, `target`) — повертає втрачені питання.
2. `task_kind`: перевіряти `apartment/house/land` раніше за `room`; `room` лише як окреме слово без числа перед ним.
3. `portal_query` і шаблони: додавати бюджет («hasta 200000», «≤ 200.000 €») і кімнати («2 habitaciones»).
4. Місто: прибрати регіональні аліаси з «на місці» для рівня «місто», додавати країну («Valencia, España» / «Valencia Spain»), відсікати Venezuela/USA за словами «Carabobo», «CA», «USD».
5. Список порталів розбити по типу задачі: квартири/будинки → Idealista, Fotocasa, Habitaclia, Pisos, Yaencontre, Kyero, Thinkspain, Milanuncios; земля → Terrenos, Sareb, Idealista; банки — лише для «дешево/від банку». Квота порталів у раунді ≤ 1/3.
6. Fail-open → fail-closed: без AI-вердикту знахідка іде у `similar`, а не `exact`; невідома ціна при заданому бюджеті — `other`.
7. SearXNG: `pageno` 1–3, `WEB_SEARCH_RESULTS_PER_QUERY` 30, прибрати 72-годинну заборону запитів для іншої кампанії, TTL 7 днів для `web_seen_urls` індексних сторінок.
8. Підняти `.env`: `CAMPAIGN_RELEVANCE_MAX_CALLS=2000`, `WEB_SEARCH_MAX_PAGES_PER_HOST=100`, `WEB_SEARCH_MAX_LINKS_PER_INDEX=40`, `WEB_SEARCH_MAX_QUERIES_PER_CAMPAIGN=80`.

### Етап 1. Доступ до порталів (3–5 днів) — головне для «без лімітів»
Три шари замість одного `httpx`:
1. **Структуровані джерела перед HTML.** Idealista має офіційний API (apikey, ~100 запитів/міс безкоштовно, платно більше); Fotocasa/Habitaclia — внутрішні JSON-ендпоїнти; у решти порталів JSON-LD/ItemList на сторінці результатів. Зберігати JSON-LD з індексних сторінок, а не викидати.
2. **TLS-імперсонація + резидентні проксі** (`curl_cffi` з профілем Chrome, браузерний UA, Accept-headers, резидентний/ISP проксі, наприклад `WEB_SEARCH_PROXY_URL` → провайдер з ротацією). Цей шар розблокує Pisos, Yaencontre, Kyero, Thinkspain, банківські портали.
3. **Браузер (Camoufox/Playwright-stealth) на 403**, а не лише на порожній текст, з лімітом рендерів у БД, не в памʼяті. Для DataDome (Idealista) — або API, або сторонній скрапінг-API (ScraperAPI / Zyte / Bright Data Web Unlocker) як останній шар; це платно, але вирішує Idealista остаточно.
4. **«Через Google по сайту»** (ідея клієнта): лишити як є — `site:` запити вже працюють так. Додати Google Programmable Search API або SerpAPI як другий бекенд поруч із SearXNG, бо з датацентру Google у SearXNG мовчить. Кожен URL із видачі → одразу спроба читання (шар 1→2→3), і лише якщо все впало — сніпет-картка з позначкою «не перевірено».
5. Блокування хоста: не глобальне 12 год, а по `(host, шар)`; 403 на шарі 1 просто переводить на шар 2.
6. Запустити `scripts/portal_probe.py` по всіх 20 порталах із VPS і зафіксувати таблицю «читається / ні / яким шаром» у `docs/PORTALS.md`. Список обовʼязкових сайтів від клієнта додати туди ж.

### Етап 2. Інтервʼюер «grill me» (3–4 дні)
1. Новий агент `bot/control_plane/interviewer.py` на сильній моделі (Fable/Opus через OpenRouter, окремий `OPENROUTER_INTERVIEW_MODEL`).
2. Промпт: дерево рішень по режиму. Питає по одному, поки всі hard-поля `TaskSpec` не заповнені або явно не позначені «не важливо». Без ліміту 3 питань; ліміт — 10 раундів і кнопка «Досить, шукай».
3. Кожна відповідь парситься у `TaskSpec`; після кожної — коротке «Зрозумів: …». Фінал — структурована картка ТЗ з кнопками «Запустити / Змінити поле / Скасувати», редагування по одному полю.
4. Голос: транскрипт показувати користувачу й підтверджувати незрозумілі слова (те, що зараз ламає баг 018).
5. Памʼять уподобань користувача між задачами (таблиця `user_preferences`).

### Етап 3. Архітектор + збирачі (4–6 днів)
1. `architect.py` → LLM-план на сильній моделі: з `TaskSpec` генерує `SearchPlan`: сайти в пріоритеті, по 5–15 запитів на мову з ціною/кімнатами/районами, URL-слаги порталів (напр. `idealista.com/venta-viviendas/valencia-valencia/con-precio-hasta_200000,de-dos-dormitorios/`), стоп-критерій («≥ 40 підтверджених або вичерпано сайти»).
2. Збирач (Sonnet) витягує з кожної сторінки строгий JSON `ListingFacts` із цитатами-доказами (вже є у `agents/extraction.py` — переналаштувати на Sonnet і увімкнути не в тіні).
3. Дедуп обʼєктів: ключ за (адреса/район + ціна ±2 % + м² ±3 % + кімнати), кластер «той самий обʼєкт на 3 сайтах» → одна картка з усіма посиланнями.

### Етап 4. Рецензент і фіналіст (3–4 дні)
1. Рецензент (Opus): для кожної знахідки — матриця hard-критеріїв `pass/fail/unknown` з цитатою; `unknown` по hard-критерію → не `exact`. Замінює `tolerance.py` + `relevance.py` одним кроком; правила ±10 % лишаються як параметр `TaskSpec`.
2. Фіналіст (Fable): коли збирачі завершили — ранжує, пише звіт: що знайдено, чому відкинуто (кількості по причинах), які сайти не прочитались і що з цим робити. Звіт користувачу, а не лише власникам.
3. Увімкнути `reduction-worker` як бойовий шлях (зняти `mode == "shadow"`), а старий analysis-worker лишити для Facebook-постів без URL.

### Етап 5. Режим «Інвестори» (4–5 днів)
1. `TaskSpec.investor`: хто (приватний/фонд/family office/девелопер), тікет, клас активу, географія, мова, роль користувача.
2. Reach: після сніпета відкривати публічні сторінки (LinkedIn company pages, сайти фондів, Telegram-канали) через той самий фетчер, витягувати контакти, опис, останню активність.
3. Скоринг 0–100 за відповідністю `TaskSpec` + дедуп людини між платформами (імʼя + компанія + місто).
4. Прибрати «startup/capital» з ключів для нерухомості; агентів/агенції/девелоперів видавати окремими групами, а не як «інвесторів».
5. Коментарі під постами FB: лишити, але лише для інвесторських кампаній (`CAMPAIGN_COMMENT_LEADS=investors`).

### Етап 6. Прибирання і спостережуваність (2 дні)
1. Видалити легасі (`bot/main.py`, `bot/services/search`, `bot/services/parser`, `google_maps.py`, другий конфіг SearXNG) або винести в `legacy/`.
2. Метрики кампанії в БД: запитів → результатів → прочитано (по шарах) → знахідок → exact/similar/excluded з причинами. Команда `/campaign report <id>`.
3. Тести: золотий набір із 10 задач (Валенсія 200k 2 кімнати, земля Мадрид, інвестори Малага …) із очікуваними запитами й порталами, запускати в CI.

## 6. Моделі й вартість (орієнтир)

| Роль | Модель | Чому |
|---|---|---|
| Інтервʼюер, архітектор, фіналіст | `claude-fable-5-1` або `claude-opus-5-5` | 1–3 виклики на кампанію, якість важливіша за ціну |
| Збирач (витяг JSON) | `claude-sonnet-5-5` | сотні викликів, строгий JSON, швидко |
| Рецензент | `claude-opus-5-5` | один виклик на знахідку, потрібна точність |
| Intake-парсер відповідей | `claude-haiku-4-5` | дешево, структурований вихід |

Кампанія на 150 сторінок: ~150 Sonnet + ~60 Opus + 3 Fable виклики. Платні
